# EventML v0.3 Library Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a library a named, versioned thing that a project references by name rather than by path, and record in library data when each requirement template applies.

**Architecture:** A library declares its identity in a manifest at its root; a project declares which library it resolves against in a manifest of its own. Both use the existing three-key header shape. The shipped example library moves under `examples/`, and the specification stops anchoring rules to a literal directory. `applies_when` joins `RequirementDef` as prose.

**Tech Stack:** Markdown (CommonMark, GitHub-flavoured tables), YAML 1.2. Verification uses ripgrep and one-off Python + PyYAML checks — neither is a repository dependency, and neither is committed.

**Source spec:** [`docs/superpowers/specs/2026-08-09-eventml-v0.3-library-design.md`](../specs/2026-08-09-eventml-v0.3-library-design.md)

**Branch:** `eventml-core-v0.3`, already created from `main`.

## Global Constraints

- **No executable code ships.** No validator, no scripts, no schema. `spec/`, `examples/` and `docs/` contain prose and data only.
- **Specification language is English.** Hungarian appears only in `docs/glossary-hu.md`.
- **Version floor is per file and marks capability.** `eventml: "0.3"` is declared by exactly the files using a v0.3 construct: every `library.yaml`, every `project.yaml`, and every library file carrying an `applies_when`. Every other file keeps the floor it has.
- **A library reference is `name@version`** — for example `eventml-example@0.2.0`. Never a path, never a URL.
- **A model resolves against exactly one library.** No search path, no fallback, no merging.
- **`eventml-core` is `0.3.0` and `eventml-lib` is `0.2.0` at this release.**
- **Released `CHANGELOG.md` sections must not be edited.** `[0.1.0]` and `[0.2.0]` are historical records.
- **Adopt, don't invent.** Where a term exists in GDTF, NMOS, IFC, SysML v2 or ISO/IEC/IEEE 42010, use it and record the source.
- **Commit after every task. Never push** — pushing is the user's decision.

- [ ] **Step 4: Write the resolution rule**

A new section in `spec/05-concrete-syntax.md`, after the reference forms. Three statements, each with its reason:

1. **A model resolves against exactly one library**, named in its `project.yaml`. There is no search path, no fallback, and no merging of two libraries. A `def:` the named library does not define is a dangling reference, not an invitation to look elsewhere. State why: a model whose vocabulary could come from two places has no answer to "what does this id mean", and the answer has to survive the person who wrote it.

2. **The reference names a library, not a place.** `eventml-example@0.2.0` says which vocabulary at which version. Where it is stored and how it is fetched belongs to whatever runs the model — a git repository, a folder, a web interface. State that this is the same separation `src:` already makes: a `src` names a `sources` entry, not a file offset.

3. **The shipped example library resolves no real project.** It exists to be read and to be copied from as a one-time seed. An organisation that copies entries owns the copies, and its library versions independently from that point.

Add a fifth row to the reference-forms table:

```markdown

```

- [ ] **Step 2: Write the section explaining it**

After the `RequirementDef` example, a short section covering:

- What it records: what a project manager knows without thinking — an outdoor event implies weather protection, a speech implies intelligibility. Today that knowledge reaches the model only if the modeller remembers; as library data it survives the person.
- That it is **prose, not an evaluable expression**, for the reason `ConstraintDef.expression` already carries: a rule needing an evaluator before an evaluator exists is written so a human or an agent can apply it, and formalising it is named for a later release.
- That nothing derives from it in v0.3. A human or an agent reads it and decides.
- That it is optional, and its absence means the template's applicability has not been written down — not that it always applies.

**Deliberate ordering.** The move precedes everything because every other task touches a path it changes. The concept restatement (Task 3) is separate from the mechanical path updates (Task 1) because a reviewer can accept one and reject the other — the first is a rename, the second is a claim about what the language means. `applies_when` precedes its worked walk so the walk has something to read. The manifest body keys are `version`, `description`, `domains` for a library and `library` for a project. `applies_when` is spelled identically in Tasks 4, 5 and 7.
