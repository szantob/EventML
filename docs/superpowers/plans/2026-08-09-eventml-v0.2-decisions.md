# EventML v0.2 Decisions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the `Decision` entity, the `affect` relation and question rule 7 to EventML, so a model can record who chose something, on what basis, and whether anyone outside the team agreed to it.

**Architecture:** One new specification file defines the entity and the criterion that governs what gets recorded. Three existing specification files gain a relation, a question rule and a file-layout entry. Two of the three worked examples gain a `decisions.yaml` that exercises every attribute. No executable code ships, exactly as in v0.1.

**Tech Stack:** Markdown (CommonMark, GitHub-flavoured tables), YAML 1.2. Verification uses ripgrep and one-off Python + PyYAML checks — neither is a repository dependency, and neither is committed.

**Source spec:** [`docs/superpowers/specs/2026-08-09-eventml-v0.2-decisions-design.md`](../specs/2026-08-09-eventml-v0.2-decisions-design.md)

**Branch:** `eventml-core-v0.2`, already created from `main`.

## Global Constraints

- **No executable code ships in v0.2.** No validator, no scripts, no schema. `spec/`, `lib/`, `examples/` and `docs/` contain prose and data only.
- **Specification language is English.** Hungarian appears only in `docs/glossary-hu.md`.
- **Version floor is per file.** A `decisions.yaml` declares `eventml: "0.2"`. The four layer files in the same project stay at `eventml: "0.1"`. Mixed floors within one project are correct.
- **Decision ids** are instance ids: `d-` prefixed, lowercase, kebab-case, no dots.
- **`affects` entries** are instance ids or brief paths — never catalogue ids.
- **`by.party` and `agreed_by.party`** take the `sources` vocabulary: `client`, `venue`, `production`, `authority`.
- **Adopt, don't invent.** Concept names come from ISO/IEC/IEEE 42010. Record the source in a `source:` key or in prose where the concept is defined.
- **Commit after every task. Never push** — pushing is the user's decision.

- [ ] **Step 1: Write `spec/07-decisions.md`**

Required sections, in this order:

1. **What a decision is** — two paragraphs. A decision records that somebody chose between options that were genuinely open, and that the model now depends on the choice. Contrast it with the constructs that already exist: an `assumed` value fills a gap in knowledge, a `sources` entry records what somebody said. State the separating sentence verbatim: **an assumption is resolved by learning, a decision by deciding again.**

2. **Where decisions live** — `decisions.yaml`, a fifth file beside the four layer files, because a decision crosses layers by nature. Show the header, and state the per-file version floor:

```yaml
eventml: "0.2"
kind: decisions
project: garden-party
---
decisions:
  - id: d-digital-transport
    ...
```

3. **Attributes** — this table exactly:

| Attribute | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | yes | Instance identifier, `d-` prefixed, no dots |
| `date` | date | yes | When the decision was made |
| `by` | map | yes | `{ party, person }`. `party` is `client` \| `venue` \| `production` \| `authority`; `person` is optional |
| `decision` | string | yes | The choice itself, in one sentence |
| `why` | string | yes | The reasoning |
| `alternatives` | list | no | Each: `option`, `why_not` |
| `affects` | list | yes | Instance ids or brief paths |
| `src` | source ref | no | The `sources` entry the decision rests on |
| `supersedes` | Decision id | no | The earlier decision this one replaces |
| `needs_agreement` | bool | no | `true` when somebody outside the team must assent |
| `agreed_by` | map | no | `{ party, person, src }` |

4. **`by` and `agreed_by`** — one section explaining that these two keys are what let a single entity carry both an engineering choice and a client agreement. An engineering choice has no `agreed_by` and needs none. A decision carrying `needs_agreement: true` and no `agreed_by` is one nobody has assented to, and question rule 7 fires on it. State that `agreed_by` cites a source rather than asserting agreement, so consent is evidence rather than memory.

5. **The recording criterion** — open by stating that ISO/IEC/IEEE 42010 requires a project to define which decisions are worth recording, and that this section is that definition. Two tests, both of which must hold:

   1. **A real alternative existed.** Where nothing else could have been chosen, the fact is a derivation and `state: derived` already holds it.
   2. **Reversal is expensive.** Where undoing it later is free, recording it is noise.

   Then this boundary table:

| When | Use |
|---|---|
| Information was missing and we filled the gap | `assumed` value with `why` |
| It follows from another value | `derived` value |
| Somebody said something | `sources` entry |
| Two sources disagree and nobody has resolved it | `conflicting` value |

   Close with the review signal: if a project's decision count approaches its requirement count, the criterion is being applied loosely. Note that this signal is what justifies the `affects` exception in `03-relationships.md`.

6. **Worked example** — the garden-party audience decision, showing a `conflicting` value being resolved:

```yaml
- id: d-audience-450
  date: 2026-08-12
  by: { party: client, person: "event manager" }
  decision: "The system is sized for 450 guests."
  why: "the guest list grew; the client confirmed the larger number"
  alternatives:
    - { option: "300 guests", why_not: "superseded by the update of 5 August" }
  affects: [brief.audience, main-pa, r-speech-intelligible]
  src: s-client-update
  needs_agreement: true
  agreed_by: { party: client, person: "event manager", src: s-client-confirm }
```

- [ ] **Step 3: Write the `affect` section**

Place it after `trace` and before `Traversal`. It must contain, in this order:

**YAML form** — `Decision.affects`, holding a list of instance ids and brief paths:

```yaml
- id: d-digital-transport
  date: 2026-08-20
  by: { party: production, person: "system engineer" }
  decision: "Stage inputs reach front of house as Dante over Cat6a, not as an analogue multicore."
  why: "45 m and 32 channels; a multicore that size is heavier and slower to derig than the crew has time for"
  alternatives:
    - { option: "16-way analogue multicore", why_not: "weight and derig time" }
  affects: [sb1, sw-stage, sw-foh]
  src: s-venue-call
```

**Cardinality** — many-to-many. One decision may determine several elements; one element may be determined by several decisions.

**Why it sits on the decision** — the two reasons, stated plainly:

- A record must read as a record. A decision whose scope is split across five files cannot be reviewed, and reviewing it is the entire purpose of keeping it.
- The backward scan is bounded. Moving `satisfy` in v0.1 avoided scanning 37 requirements; the recording criterion in `07-decisions.md` holds decisions to roughly ten per project, and scanning ten entries costs nothing.

Then the sentence that makes the exception checkable: the second reason is also a check on the first, so if a project accumulates as many decisions as requirements, the fault lies in the recording rather than in the relation.

**When the edge is absent** — a decision with no `affects` determined nothing, which means it is not a decision. Unlike the other relations, an empty `affects` is a modelling error rather than a question.

**`supersedes`** — one paragraph noting it obeys the ordinary rule. It sits on the newer decision, so walking a decision's history backward stays a field read.

- [ ] **Step 2: Write the rule**

Place it after Rule 6, before the `## 4. Ranking` heading:

```markdown
#### Rule 7 — a decision nobody has agreed to

**Trigger.** A `Decision` carrying `needs_agreement: true` and no `agreed_by`.

Somebody outside the team has to assent to this and has not. The decision may
already be built into the design, ordered, and on the truck — nothing about an
unagreed decision stops the work, which is exactly why it needs surfacing before
the invoice does it instead.

`needs_agreement` is set by the author rather than derived, which repeats a
pattern the language already justifies: `ask: true` on an assumed value records
the judgement at the point where it is made, by the only person able to make it.
Whether a choice needs the client's assent is the same kind of judgement.

Like rules 3 and 6 the question is addressed to the project manager, though
answering it usually means contacting somebody else.

```yaml
- ask: "Can you confirm we are leaving out the backup generator? We agreed it in July but never put it in writing, and it means the show stops if the supply fails."
  why: "d-no-backup-genset is unagreed and it moves a risk onto the client"
  blocks: 0
```
```

## Self-Review

**Spec coverage.** Every section of the design record maps to a task. §4.1 the entity → Task 1; §4.2 the `affect` relation and its exception → Task 2; §4.3 question rule 7 → Task 3; §4.4 the recording criterion → Task 1 Step 1 §5; §5 standards adopted → Task 6; §6 verification → Tasks 4, 5 and 8; §7 files touched → all tasks, with the four stale promises in Task 7; §8 exclusions → nothing to implement. D14's per-file version floor is enforced in Task 1 Step 1, Task 7 Step 1 and Task 8 Step 4.

**Deliberate ordering.** The entity precedes the relation because the relation has nothing to attach to otherwise, and both precede the examples because the examples are written against them. The examples precede the SysML mapping, following the v0.1 precedent that a mapping should describe a construct already exercised. The stale-promise correction sits in Task 7 rather than Task 1 so that a reviewer sees the release-plan change as one decision rather than as a detail buried in a specification edit.

**Type consistency.** Attribute names are spelled identically in every task: `id`, `date`, `by`, `decision`, `why`, `alternatives`, `option`, `why_not`, `affects`, `src`, `supersedes`, `needs_agreement`, `agreed_by`. The actor shape is `{ party, person }` throughout, and `agreed_by` alone adds `src`. The relation is `affect` in prose and `affects` as the attribute, matching how `satisfy`/`satisfies` and `refine`/`refines` already read. Question rule 7 is `rule: 7` in both example question lists.

**Known gap, accepted.** Question rule 7 fires on `needs_agreement: true` with no `agreed_by`, and nothing checks that an author set `needs_agreement` where they should have. The same gap exists for `ask: true` on assumed values and is accepted for the same reason: the judgement belongs to the person making the decision, and no rule can infer it. A validator will not close this in v0.5 either.
