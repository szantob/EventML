# EventML v0.2 — Decisions — Design

**Status:** approved, ready for planning
**Date:** 2026-08-09
**Supersedes nothing.** Extends [`2026-08-08-eventml-core-design.md`](2026-08-08-eventml-core-design.md).

---

## 1. Context

v0.1 models what a system is and where every part of it came from. It does not model *who chose it*. A
model can say that a stage box exists, that it realises a mix position, and that the mix position meets a
speech requirement traced to a client email. It cannot say that the stage box exists because somebody chose
Dante over an analogue multicore, that a named engineer made that choice on a named day, or that the client
never agreed to it.

The gap is visible in the shipped repository. `examples/01-garden-party/README.md` explains in prose that
"the stage box and the switches exist only because a digital transport was chosen at L3." That sentence is
the most valuable line in the example and the model cannot hold it.

### Why this release, and not the formalisation

The shipped specification promises that formalising the metamodel is "the first task of v0.2." That
ordering is now wrong, and this design changes it. Freezing a schema over the current kernel and then
adding an entity, a relation and a question rule would discard most of the schema work. The core design
record already settled the principle in D6 — *settle concepts before freezing them* — and the same
reasoning applies one release later.

### The four releases

The user's requirement — "how do continuous communication and decision processes appear?" — decomposes into
three independent subsystems. Each gets its own design, plan and implementation cycle.

| Release | Subsystem | Why in this position |
|---|---|---|
| **v0.2** | **Decisions — accountability** | The most self-contained. `sources` and the `sender` field already exist beneath it |
| v0.3 | Question lifecycle — live coordination | Conflicts with the rule that the question list is derived, never authored. A derived list cannot carry state, and resolving that needs its own design |
| v0.4 | Baselines and revisions — change management | The largest, and it builds on both of the above |
| v0.5 | Formalisation — schema, validator, derived question list | Written over the settled kernel |

**This document covers v0.2 only.**

## 2. What ships in v0.2

One new entity, one new relation, one new question rule, one new file per project that needs it, and the
prose that governs all four. No executable code, exactly as in v0.1 — the constraint holds until v0.5.

- `spec/07-decisions.md` — the `Decision` entity, the recording criterion, the `by`/`agreed_by` split
- The `affect` relation, added to `spec/03-relationships.md`
- Question rule 7, added to `spec/04-uncertainty.md`
- `decisions.yaml` in two of the three examples

## 3. Decisions

| # | Decision | Rationale |
|---|---|---|
| D8 | **`Decision` is a standalone entity**, not an attribute on the affected element and not a sixth value state | Only a standalone entity can express a structural choice — one that causes three devices to exist rather than setting one value. A value state fails the motivating example outright |
| D9 | **One entity for engineering choices and client agreements**, distinguished by `by` and `agreed_by` | Both answer the same question — who chose this, and on what basis. Splitting them would duplicate every attribute and force an arbitrary call on decisions that are both |
| D10 | **Concepts adopted from ISO/IEC/IEEE 42010**, names included | The architecture description standard already models Architecture Decision and Architecture Rationale. Rule 8 of the repository conventions requires adopting rather than coining |
| D11 | **`affects` is stored on the `Decision`**, against the rule that every edge sits at its lower end | A decision record must be readable as a record; scattering its scope across five files defeats the purpose. Stated in the specification as a deliberate exception, with its cost |
| D12 | **An explicit recording criterion ships with the entity** | ISO 42010 requires it, and without it the one-entity choice in D9 lets everything pour in |
| D13 | **`raises` is deferred to v0.3** | 42010 lets a decision raise new concerns. In EventML that means opening a question, which is question-lifecycle work. Accountability does not need it |
| D14 | **The version floor rises to `eventml: "0.2"` only for files using the new construct** | A project that records no decisions stays valid 0.1. The floor marks capability, not calendar |

## 4. Architecture

### 4.1 The `Decision` entity

Decisions live in `decisions.yaml`, a fifth file beside the four layer files. A decision crosses layers by
nature — the transport choice decides at L2 and causes devices at L3 — so no layer file can own it.

The header keeps three keys. `kind` replaces `layer`, carrying the meaning it already has in library files:

```yaml
eventml: "0.2"
kind: decisions
project: garden-party
```

The floor is per file, as the existing convention already makes it. A project that records decisions
carries `"0.2"` in `decisions.yaml` and leaves its four layer files at `"0.1"`, because those files use
nothing the earlier language lacked. Mixed floors within one project are correct, not an oversight.

| Key | Required | ISO 42010 | Meaning |
|---|---|---|---|
| `id` | yes | — | Instance identifier, `d-` prefixed, no dots |
| `date` | yes | — | When the decision was made |
| `by` | yes | — | Who made it: `{ party, person }`. `party` takes the `sources` vocabulary — `client`, `venue`, `production`, `authority`; `person` is optional |
| `decision` | yes | — | The choice itself, in one sentence |
| `why` | yes | Architecture Rationale | The reasoning |
| `alternatives` | no | alternatives not chosen | List of `{ option, why_not }` |
| `affects` | yes | affects AD Elements | What the decision determined. Each entry is an instance id (a `Part`, `Connection`, `Flow` or `Requirement`) or a brief path — the same two reference forms `05-concrete-syntax.md` already defines. Catalogue ids are not valid: a decision governs one project, not the library |
| `src` | no | citations to sources | The `sources` entry it rests on |
| `supersedes` | no | decisions depend on decisions | The earlier decision this one replaces |
| `needs_agreement` | no | — | `true` when somebody outside the team must assent |
| `agreed_by` | no | — | Who assented: `{ party, person, src }` |

`by` and `agreed_by` are what let one entity carry both kinds of decision. An engineering choice has no
`agreed_by` and needs none. A decision that changes what the client pays for or receives carries
`needs_agreement: true`, and until `agreed_by` appears, nobody has assented — which is precisely the fact a
dispute turns on.

`agreed_by` cites a source rather than asserting agreement, so consent is evidence, not memory.

### 4.2 The `affect` relation

`affect` joins `refine`, `derive`, `satisfy`, `allocate` and `trace` as the sixth relation, and it breaks
their shared rule. The other five sit at the lower, more concrete end of the edge, which makes tracing
backward a chain of field reads. `affects` sits on the decision instead.

The specification states this as an exception and gives both reasons:

- **A record must read as a record.** A decision whose scope is split across five files cannot be reviewed,
  and reviewing it is the entire purpose.
- **The backward scan is bounded.** Moving `satisfy` in v0.1 avoided scanning 37 requirements. The recording
  criterion holds decisions to roughly ten per project, and scanning ten entries costs nothing.

The second reason is also a check on the first. If a project accumulates as many decisions as requirements,
the criterion is being applied loosely — the fault lies in the recording, not the relation. The
specification says so, so that the exception rests on something observable rather than on a promise.

`supersedes` obeys the ordinary rule: it sits on the newer decision, so walking a decision's history
backward stays a field read.

### 4.3 Question rule 7 — an unagreed decision

**Trigger.** A `Decision` carrying `needs_agreement: true` and no `agreed_by`.

`needs_agreement` is set by the author, not derived, which repeats a pattern the language already uses and
justifies: `ask: true` on an assumed value records the judgement at the point where it is made, by the only
person able to make it. Whether a choice needs the client's assent is the same kind of judgement.

Like rules 3 and 6, the question addresses the project manager rather than the client, though its answer
usually requires contacting them.

### 4.4 The recording criterion

ISO 42010 states that recording every decision is impractical and that a project must establish criteria
for selecting the ones worth recording. Two tests, both of which must hold:

1. **A real alternative existed.** Something else could have been chosen. Where nothing could, the fact is
   a derivation, and `state: derived` already holds it.
2. **Reversal is expensive.** Undoing it later costs money, time, or an awkward conversation. Where reversal
   is free, recording it is noise.

The boundary against constructs that already exist:

| When | Use |
|---|---|
| Information was missing and we filled the gap | `assumed` value with `why` |
| It follows from another value | `derived` value |
| Somebody said something | `sources` entry |
| Two sources disagree and nobody has resolved it | `conflicting` value |

One sentence separates the two that are easiest to confuse: **an assumption is resolved by learning, a
decision by deciding again.** If the arrival of missing information settles it, it was an assumption.

The two meet where a `conflicting` value gets resolved. The garden party's audience count is `conflicting`
today — 300 in the first email, 450 in the second. Choosing 450 is a decision, made by the client, citing
the email, and it demonstrates D9 in one record.

## 5. Standards adopted

| Standard | What it gives | How EventML uses it |
|---|---|---|
| ISO/IEC/IEEE 42010 | Architecture Decision and Architecture Rationale; the relations *affects*, *pertains to*, *raises*; the requirement that a project define recording criteria | Concept names and attribute meanings taken directly. *affects* adopted, *raises* deferred to v0.3, *pertains to* not adopted — EventML has no Concern entity, and `Requirement` covers the need |
| SysML v2 / KerML | Metadata as a first-class annotating element with identity and lifecycle, pointing at annotated elements | The structural precedent for D8: an annotation with its own identity, not a field on the thing it annotates |

ISO 42010 joins the standards table in `README.md` and `spec/00-overview.md`. It is the first standard
EventML adopts that is not a modelling language or a device format, and it belongs there: EventML is an
architecture description, and 42010 is the standard for those.

## 6. Verification

v0.2 has no validator, so the examples carry the burden under the same two rules as v0.1, plus a third.

1. Every concept defined in `spec/` appears in at least one example.
2. Every example remains walkable end to end across all four layers.
3. **New:** every `affects` reference resolves to an element that exists, and every `supersedes` reference
   to a decision that exists.

Two examples gain a `decisions.yaml`, and each proves something the other cannot:

- **`01-garden-party`** — the full set: an engineering choice that causes three devices to exist, a client
  agreement resolving the `conflicting` audience count, and an unagreed decision that fires rule 7.
- **`03-festival-stage`** — a `supersedes` chain, and a decision resolving the cable-route conflict between
  the site manager and the council representative. That conflict already sits in the model unresolved, and
  it is the only place where a decision must settle a disagreement between two outside parties.

`02-conference-room` gains nothing. It would repeat what the other two already show.

## 8. Explicitly not in v0.2

Question lifecycle and status. Assignees and due dates. Baselines, revisions and model diffing. A `Concern`
entity. Any schema, validator or derived question list. Each belongs to a later release named in section 1,
and each would enlarge this one past what a single implementation plan should carry.
