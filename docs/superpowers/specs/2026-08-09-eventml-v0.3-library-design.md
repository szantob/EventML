# EventML v0.3 — The library as a named thing — Design

**Status:** approved, ready for planning
**Date:** 2026-08-09
**Extends:** [`2026-08-08-eventml-core-design.md`](2026-08-08-eventml-core-design.md), [`2026-08-09-eventml-v0.2-decisions-design.md`](2026-08-09-eventml-v0.2-decisions-design.md)
**Origin:** [issue #2](https://github.com/szantob/EventML/issues/2), with the scope revised during brainstorming — see §1.

---

## 1. Context

v0.1 and v0.2 built a language for describing one event. Neither says where the vocabulary that event is
described in comes from. `spec/02-metamodel.md` states that "definitions live in `lib/`", pointing at a
directory in this repository as though it were the language's catalogue. It is not: it is one example of a
catalogue, and every organisation modelling real events will have its own.

That confusion has already produced a contradiction. Issue #2 proposes the rule that "a model resolves
against exactly one library, and the shipped `lib/` is part of no project's resolution" — but the three
worked examples under `examples/` are models, and their `def:` references resolve against the shipped
`lib/` today. Under the rule as issued, this repository's own examples would be non-conforming.

### What changed during brainstorming

The issue scoped three prose-and-data changes. Two decisions taken during brainstorming make the release
larger and, in one place, reverse an argument made earlier in this project.

**References must be portable across storage substrates.** The intended consumers run in a git repository,
a folder on a machine, and a web interface. A filesystem path is meaningless in the third, so the reference
cannot be a path. The specification defines the *reference*; each host resolves it in its own way. This is
the same separation `src:` already makes — a `src` names a `sources` entry, not a file offset.

**A reference names a version as well as a name.** This reverses an argument made earlier in this project's
history. When the shipped library's status was first questioned, the reasoning ran: the library is a seed
to copy rather than a dependency to track, so versioning it separately is meaningless. That reasoning was
wrong, because versioning is not a property of *the shipped library being a dependency*; it is a property
of *libraries in general being referenceable*. Once a model names the vocabulary it was built against,
every library must version itself — the organisation's own most of all.

The payoff is already sitting in this repository. `examples/02-conference-room/brief.yaml` opens with the
client sentence *"Same as last year but the streaming part is new."*, and that example's README calls it
"the most dangerous sentence in the brief" precisely because "same as last year" refers to a model nobody
wrote down. A name-and-version reference makes that sentence resolvable.

### Roadmap position

Issue #2 moves applicability work forward, and the question lifecycle back. The releases now read:

| Release | Subsystem |
|---|---|
| v0.1 | The kernel — layers, entities, relations, uncertainty |
| v0.2 | Decisions — accountability |
| **v0.3** | **The library as a named thing, and requirement applicability** |
| v0.4 | Question lifecycle — live coordination |
| v0.5 | Baselines and revisions — change management |
| v0.6 | Formalisation — schema, validator, derived question list |

The shipped specification names only v0.5 for formalisation, in four places. **Those four must move to v0.6**
— see §7.

## 2. What ships in v0.3

Two subsystems. They are independent, and if the release grows too large the second is what lifts out.

**The library as a named thing.** A library declares its own identity in a manifest. A project declares
which library it resolves against, by name and version. A resolution rule states that a model resolves
against exactly one library. The shipped example library moves under `examples/` and is named for what it
is.

**Requirement applicability.** `applies_when` on `RequirementDef`, stating in one sentence when a template
applies. Prose, not an evaluable expression.

They are kept together because both serve the same consumer — the organiser building a catalogue before any
event is planned — and because `applies_when` is library content, so it lands in the file kind the first
subsystem is reshaping anyway.

---

## 3. Decisions

| # | Decision | Rationale |
|---|---|---|
| D15 | **A library declares its identity in a manifest**, not in every file's header | One place to state a version. Repeating it across twenty domain files is the duplication v0.2 twice had to clean up, and it would drift the first time somebody edited one file |
| D16 | **The reference names `name@version`, not a location** | It has to mean the same thing in a git repository, a folder and a web interface. A path means something in the first two and nothing in the third. The specification defines the reference; the host defines resolution |
| D17 | **A project declares its library in a project manifest**, not in a fourth header key | Symmetric with the library manifest, states the reference once rather than in every layer file, and leaves the three-key header rule intact. It is also where v0.5's baselines will land, so the file kind is introduced once |
| D18 | **The example library moves to `examples/lib/`** | Structure states the status that prose otherwise has to. A top-level `lib/` looks normative however carefully the text denies it |
| D19 | **The specification names the concept, not the path** | "Definitions live in a library" rather than "definitions live in `lib/`". The rule is about the language; the directory is an accident of this repository |
| D20 | **`applies_when` is prose** | The same reasoning `ConstraintDef.expression` already carries: a rule that needs an evaluator before an evaluator exists is written so a human or an agent can apply it, and formalising it is named for a later release |
| D21 | **`eventml-lib` keeps versioning separately, and the principle generalises** | Every library versions itself, not only the shipped one. `eventml-lib` is not special; it is the first instance of a general rule |

## 4. Architecture

### 4.1 The library manifest

`library.yaml` at the library root. Its header uses the existing three-key shape: the third key has always
named the thing a file belongs to — `domain` for a library's domain files, `project` for a model file — and
for a manifest that is `library`.

```yaml
eventml: "0.3"
kind: library
library: eventml-example
---
library:
  version: "0.2.0"
  description: >-
    The vocabulary the worked examples resolve against. Illustrative: copy entries from it as a one-time
    seed, and do not resolve a real project against it.
  domains: [audio, lighting, video, network, power]
```

| Key | Required | Meaning |
|---|---|---|
| `version` | yes | The library's own version, independent of `eventml-core` |
| `description` | yes | What this library is for, and whom it belongs to |
| `domains` | yes | The domain directories this library contains |

The domain files — `items.yaml`, `ports.yaml`, `parts.yaml`, `requirements.yaml` — are unchanged. The
manifest covers them.

### 4.2 The project manifest

`project.yaml` beside the layer files, mirroring the library manifest.

```yaml
eventml: "0.3"
kind: project
project: garden-party
---
project:
  library: eventml-example@0.2.0
```

A project directory therefore holds: `project.yaml`, the four layer files, and `decisions.yaml` when the
project records decisions.

### 4.3 The resolution rule

Three statements, in `spec/05-concrete-syntax.md`:

- **A model resolves against exactly one library**, named in its `project.yaml`. There is no search path, no
  fallback and no merging of two libraries. A `def:` that the named library does not define is a dangling
  reference, not an invitation to look elsewhere.
- **The reference names a library, not a place.** `eventml-example@0.2.0` identifies which vocabulary at
  which version; where that vocabulary is stored, and how it is fetched, belongs to whatever is running the
  model.
- **The shipped example library resolves nobody's real project.** It exists to be read, and to be copied
  from as a one-time seed. An organisation that copies entries from it owns the copies, and its own library
  versions independently from that point.

### 4.4 Moving the example library

`lib/` becomes `examples/lib/`, carrying a manifest that names it `eventml-example`. The three worked
examples each gain a `project.yaml` naming it.

This mixes categories inside `examples/`, which currently means "worked models exercising all four layers".
A library is not a model. Rather than leave that unstated, `CLAUDE.md` and `README.md` describe the
directory as holding the worked models **and the library they resolve against** — which is what it will
contain.

### 4.5 `applies_when`

An optional key on `RequirementDef`, holding one sentence about when the template applies.

```yaml
- id: audio.req.speech_intelligibility
  name: Speech intelligibility
  applies_when: "the brief has any spoken-word programme item — a speech, a ceremony, a panel discussion"
  text: "Speech must be intelligible across {area} for an audience of {audience}."
```

It records what a project manager knows without thinking: an outdoor event implies weather protection, a
speech implies intelligibility. Today that knowledge lives in the modeller's head and reaches the model only
if they remember. As library data it survives the person.

Nothing evaluates it in v0.3. A human or an agent reads it and decides whether the template applies, exactly
as they already do with a `ConstraintDef.expression`.

### 4.6 Version floors

The floor stays per file and marks capability, as v0.2 established. `eventml: "0.3"` is declared by exactly
the files that use a v0.3 construct: every `library.yaml`, every `project.yaml`, and every library file
carrying an `applies_when`. Everything else keeps the floor it already has — a brief written in v0.1
constructs stays `"0.1"` even in a project whose `project.yaml` is `"0.3"`.

At this release `eventml-core` is `0.3.0` and `eventml-lib` is `0.2.0`. Those two numbers are independent
of any file's floor, and after D21 `eventml-lib` is simply the first library to carry a version of its own
rather than a special case.

## 5. What this changes in existing prose

The specification currently anchors rules to a path. Three statements become false on the move and must be
restated in terms of the concept:

| Today | After |
|---|---|
| "Definitions live in `lib/`" (`spec/02-metamodel.md`) | Definitions live in a library |
| "All of them may appear in `lib/`; none of them may appear in a model file" | …may appear in a library… |
| "Four entities are usages… none of them may appear in `lib/`" | …none may appear in a library |

Three further statements say the catalogue is "shared across projects" (`spec/02-metamodel.md` twice,
including the Mermaid diagram's label, and `spec/06-sysml-mapping.md`). These are not false — the
surrounding sentence makes clear it means one organisation's catalogue mapping onto its rental inventory —
but they do not say *whose* projects, and the diagram's label attaches the claim directly to the shipped
`lib/`, which is the reading v0.3 retires. Sharpen all three to name the organisation.

---

## 6. Verification

No validator ships in v0.3, so `examples/` carries the burden under the two existing rules, plus two more:

1. Every concept defined in `spec/` appears in at least one example. **`CLAUDE.md` states this rule as
   "defined in `spec/` or `lib/`"; that path moves, so the rule must be restated against the library's new
   location rather than left pointing at a directory that no longer exists.**
2. Every example is walkable end to end across all four layers.
3. **New:** every `library:` reference resolves to a manifest that exists, matching on both name and
   version.
4. **New:** at least one example README derives by hand which requirement templates its brief triggers,
   showing the intended use of `applies_when` — an illustration of derived output, exactly as the
   hand-written question lists are.

of plan belongs in the new entry.

## 8. Explicitly not in v0.3

Namespace handling, and what happens when two libraries define the same id. Any evaluator for
`applies_when`. Question lifecycle and question state. Baselines and revisions. Schema or validator. The
`eventml-skills` toolkit — its command surface, the division of labour between scripts and agents, and how
a catalogue builder is verified are all still open, and none of them is a language question.
