## 1. How this release got to its subject

The session opened on what `spec/00-overview.md` §5 lists as the next item — the question lifecycle — and
walked backwards four times. Each step found something missing underneath the last, and the record of the
walk matters more than usual, because it is the argument for why this release is as small as it is.

**Step 1 — from the question to the change.** The lifecycle was going to cover the outbound question and
its states. But a client can invalidate work by simply writing a new email, with no question involved: a
new source arrives and a requirement goes stale. The question is one trigger of change, not change itself.

**Step 2 — from the change to what produces a decision.** Retirement raised the obvious next question:
what makes an element stale in the first place? Something must happen between "the check reports a gap" and
"the plan changed", and that something is a choice — a `Decision`. The language holds the record of a
decision but says nothing about what produces one.

**Step 3 — from the decision to the library.** The project-management logic that turns a gap into a choice
belongs in the library, on `RequirementDef`, which already carries most of it — see §5. What it does not
carry is what to do when the information does not arrive.

**Step 4 — from the logic to the types.** Writing that logic per template means writing it 22 times. Before
it can be written once, the library has to say what kinds of requirement it deals with — and nothing in the
language lets it say that.

So the subject of this release is the bottom of that stack: **a library declares the kinds of requirement
it handles.** Everything above it waits.

## 2. What is settled

| # | Decision | Rationale |
|---|---|---|
| D51 | A library declares the kinds of requirement it handles | The language provides the slot; the library fills it. Exactly the move ISO/IEC/IEEE 42010 makes for decision recording criteria, which `spec/07-decisions.md` §5 already adopted: the standard requires the project to state its own criterion rather than fixing one |
| D52 | The declaration is a standalone list in the library, not a bare label on each template | A list can be read and questioned on its own — *how many kinds does this system work with, and is the list complete?* A set inferred from labels cannot answer that |
| D53 | Each `RequirementDef` names the kind it belongs to | The classification has to be usable from the template, and it is what a check reads |
| D54 | A kind carries a name and a description, and no project-management logic | Deliberately minimal. What to do when information is missing is the next release's subject, and putting it here before the kinds have been exercised would freeze a guess |
| D55 | EventML does not fix the taxonomy | The vocabulary belongs to whoever owns the library — the v0.3 ownership rule. A library that wants SysML's categories may use and cite them; one that derives its own from its domain may do that instead |

**D55 also dissolves a rule 8 problem.** Rule 8 says adopt a standard's term where one exists and coin only
where none does. A taxonomy fixed by the language would have forced that judgement once, globally. A
declared taxonomy moves it to whoever writes the library, where it belongs, and the language coins nothing.

## 3. The open question

**What does the type list check?** Asked and not answered. The three options as they were put:

- **Both.** From the library side, every `RequirementDef` names a declared kind and the name resolves — a
  script decides this. From the model side, every declared kind either has a requirement in the project or
  a written reason why it has none — judgement, but with something to measure against for the first time.
  This second half is what answers the question that started step 4.
- **Library only.** Check that every template is classified and every name resolves. Cheap, purely
  syntactic, demands nothing of projects. Leaves "did we miss a kind?" unanswered.
- **Model only.** Ask projects to account for every declared kind, and leave the library's classification
  advisory. A mistyped kind name would then go unnoticed.

Nothing else in §2 depends on this answer, so the rest of the design can be written either way — but the
release's value rests on it.

## 4. What comes after, and why in this order

The four steps of §1 read backwards give the release order. Each depends on the one before it.

1. **This release.** A library declares its requirement kinds.
2. **Project-management logic.** What a requirement kind implies about missing information: who can answer
   it, what to do when nobody does, how a conflict of that kind resolves, and whether an applied default is
   silent or must be owned by somebody. Written per kind rather than per template.
3. **What produces a decision.** The moment a gap stops being waited on and becomes a choice, and the
   `Decision` that records it. Only reachable once (2) says what the choice is between.
4. **How the model survives a change.** Retirement — an element saying it is no longer in force. See §5 for
   what was already established about its shape.
5. **The question lifecycle.** The outbound question and its states, which is where this session began.

Formalisation and tooling stay after all of these, as `spec/00-overview.md` §5 already says.

## 5. Findings worth keeping

**`RequirementDef` already carries most of the project-management logic**, under other names. Counted across
the 22 templates in `examples/lib/*/requirements.yaml`:

| Attribute | The question it answers | Templates carrying it |
|---|---|---|
| `applies_when` | When does this requirement come into play at all? | 22 |
| `params` | What information is needed to state it? | 22 |
| `params[].default` | What is used if nobody says? | 28 entries |
| `asks` | How is a non-expert asked for what is missing? | 28 entries |
| `constraints` | What must hold for it to be met? | 8 |
| `verification` | How would anyone check it was met? | 22 |

Three things are missing, and all three sit at the moment somebody has to decide: nothing says **which
defaults may be applied silently and which are a choice somebody must own**; nothing says **when a gap stops
being waited on**; and nothing says **how a conflict of a given kind is resolved**. These are release 2 in §4.

**The project-management logic splits by *origin*, not by the nature of the requirement.** Grouping the 22
templates by their `applies_when` sentence gives four clusters, and what to do about missing information
differs by cluster because *who could answer* differs:

| Cluster | Brought in by | Templates | Missing information is resolved by |
|---|---|---|---|
| Programme | what the client wants to happen | 7 | Asking the client |
| Site | where the event is | 5 | Measuring or photographing, not asking an opinion |
| Consequential | our own design | 8 | Calculating or designing; the client cannot answer |
| Regulatory | an authority or a standard | 2 | Nothing — it is met, and compliance is evidenced |

`power.req.supply_capacity` is the awkward one: its `applies_when` is "always", and it is neither programme
nor regulation but engineering necessity.

**This clustering is a finding, not a decision.** It was offered as a fixed taxonomy and rejected in favour
of D55. It is recorded because release 2 will need to know what actually differs, and because it explains
why SysML's categories do not map cleanly: **SysML classifies by the nature of the requirement — functional,
performance, interface, physical, design constraint — while this domain's logic splits by origin.** Two
axes, which is why the mapping was awkward when tried:

| Origin cluster | Nearest SysML category | Verdict |
|---|---|---|
| Programme | `functionalRequirement` | Fits |
| Regulatory | `designConstraint` | Fits |
| Site | `physicalRequirement` | Does not: SysML's constrains the *system's* physical properties, ours describes the *environment* constraining the system |
| Consequential | `interfaceRequirement` | Too narrow: covers the link cases only, not universe counts or redundancy |

SysML's five categories are **non-normative** in the specification, which is what makes them a starting
vocabulary rather than a contract. SysML v2's recommended mechanism for requirement hierarchies is
**specialization** of `requirement def` rather than the v1 `deriveReqt` dependency.

**Retirement, established before the walk moved on.** Kept for release 4:

- The reason it must live in the model rather than in git history is **checkability**. The v0.4 checks are
  pairwise, so deleting an element silences exactly the check that fired on it — deletion becomes a way to
  make a report clean, with nothing recording that a choice was made. The same failure the language already
  refuses for a `conflicting` value.
- **Retirement is a property of an element; replacement is an edge between two.** They were conflated once
  and should not be again. `Decision.supersedes` is the replacement edge and needs no change. Retirement
  cannot be an edge, because the common case is that nothing takes the retired element's place, and an edge
  has no end to sit on.
- Retirement belongs on every element a check can fire on: `Need`, `Requirement`, L2 `Part`, and `Decision`
  — the last because rule 7 fires on it, so deleting it silences a finding too.
- Three reasons an element goes stale, worth keeping apart: the client changed their mind (history, and it
  explains billed work), an assumption was falsified (the basis moved), and we made a mistake (a correction,
  not history).

Two process notes from this session, both worth remembering because they were corrections:

- **Do not describe the metamodel in terms of files.** Say what an element is in the model, not which file

  better explanation than the file-based one it replaced, which is the argument for the rule.
