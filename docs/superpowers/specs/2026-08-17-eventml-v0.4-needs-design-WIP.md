## 1. What this release is for

The client says "I never asked for that." Today the model cannot settle the argument in either
direction. It cannot show that every request in an email produced something, and it cannot show
that every line on the quote traces back to something somebody asked for.

The release makes both checkable.

## 2. The three levels, settled

The central result of the brainstorm. The middle level did not exist as an addressable thing
before, and its absence is why neither check was possible.

| Level | What it is | State |
|---|---|---|
| **Source** | Raw text, whole and unmodified — an email, a call note, a meeting transcript | Exists today as `brief.sources` |
| **Need** | Still the client's words, broken into elementary units of information | **New in v0.4** |
| **Requirement** | The technical requirement derived from a need | Exists today as L1 `Requirement` |

A source is never decomposed. Granularity lives in the *reference*: a `src` names a passage
within the source's text. The atomising happens one level up, as `Need` entities.

## 3. Decisions settled during the brainstorm

| # | Decision | Rationale |
|---|---|---|
| D22 | **`Need` is a new entity in the L0 Brief layer** | The middle level needs to be addressable for either completeness check to run |
| D23 | **The name comes from ISO/IEC/IEEE 29148's *stakeholder needs*** | 29148 separates stakeholder needs (OpsCon) from system requirements (SyRS), and its SyRS definition — "transform the stakeholder, user-oriented view into a technical view" — is exactly what EventML's `Requirement` already is. `StakeholderRequirement` was rejected: two "requirement" words in one language invites permanent confusion |
| D24 | **The layer keeps the name `brief`** | `layer: brief` sits in every model file, the spec, the glossary and three examples, and "the brief" is what a project manager actually says. A layer's name and its entity's name need not match — L2 is Logical and holds `Part`s |
| D25 | **A source is never decomposed; it stays monolithic** | Keeps L0's raw material raw, and avoids a classification taxonomy (request / fact / preference) whose boundaries would be argued forever |
| D26 | **Passage references adopt the W3C Web Annotation Data Model** | Both selectors, deliberately redundant: `exact` is the durable anchor, `start`/`end` stay current under editing, and when they disagree the break is visible. The standard states this redundancy is the point |
| D27 | **`Need.value` is optional, and the uncertainty model is untouched** | Where a need carries a quantity it uses the existing `state` / `alternatives` / `why` / `ask` machinery unchanged. Where it does not — a speech, a quality expectation — it is text only |
| D28 | **`Requirement.refines` retargets from a brief path to a `Need` id** | A simplification: `refines` becomes an ordinary instance reference like every other edge, and the brief-path reference form largely disappears |
| D29 | **One edge between sources: `answers`** | The process, not the thread. YAGNI: a second edge waits for an example that needs it |
| D30 | **No `topic` or grouping key on `Need` at first** | Today's nested brief map (`venue`, `power`, `program`) flattens to a list. If an example demands grouping, that is the argument for adding it |

## 4. What §1 of the design established

`Need`, as approved:

```yaml
needs:
  - id: n-audience
    text: "about 300 people"
    src: { id: s-client-brief, exact: "about 300 people", start: 36, end: 52 }
    value:
      state: conflicting
      alternatives:
        - { value: 300, src: { id: s-client-brief, exact: "about 300 people", start: 36, end: 52 } }
        - { value: 450, src: { id: s-client-update, exact: "we're now looking at 450" } }

  - id: n-welcome-speech
    text: "There'll be a welcome speech around 7"
    src: { id: s-client-brief, exact: "There'll be a welcome speech around 7", start: 93, end: 130 }
```

`text` holds the client's words, not a paraphrase. The offsets above are real, measured against
the excerpt as it stands in `examples/01-garden-party/brief.yaml`.

## 5. The two checks this enables

Both run **layer by layer**, not across the whole chain. That was a correction made during the
brainstorm: an earlier draft tried to check source-to-requirement directly and could not, because
the intermediate step was missing.

- **Which passages of a source no `src` cites.** Not "which requests lack a requirement" — the
  model cannot know which sentences were requests without a taxonomy it deliberately does not
  have. It reports unreferenced text and leaves the judgement to a human, the same division of
  labour question rules 3 and 6 already use.
- **Which `Need` no `Requirement` refines**, and **which `Requirement` refines no `Need`.** The
  second is the "I never asked for that" case. `spec/03-relationships.md` already says an absent
  `refines` "should be visible in review" — nothing surfaces it, and all three examples contain one.

## 6. Open — resume here

1. **Sections 2 onward of the design were never presented.** The coverage rules, the `answers`
   edge, what changes in existing prose, and verification all still need writing and approval.
2. **What happens to today's nested brief structure.** D30 says flatten, but no example has been
   rewritten to see whether that reads acceptably. The garden party brief is the test.
3. **Whether the `sources` list moves out of `brief.yaml`.** Raised twice and deferred twice. With
   three levels rather than two, the sources are now clearly the material the brief was made
   *from* rather than part of it. The user's own reasoning pointed here; no decision was taken.
4. **Question lifecycle is explicitly out of scope** and moves to the release after this one:
   outbound letters, asked/answered/unusable state, and ISO 42010's `raises` relation deferred by
   v0.2's D13. Much of it becomes derivable once `answers` exists.

## 7. A finding worth keeping

**SysML does not solve the passage-reference problem, because it never meets it.** Its
requirements are already model elements by the time it sees them; the document-to-requirement
step happens beforehand in a requirements tool, using ReqIF, which decomposes a document into
identified `SpecObject`s. EventML deliberately models the stage *before* that — the raw client
email — so rule 8's usual list has no answer here, and W3C Web Annotation was adopted instead.

## 8. A process note

Formalisation has now been renumbered three times (v0.2 → v0.5 → v0.6, and this release would
make it v0.7). Every renumbering left stale promises in shipped prose that the reviews had to
catch. **Shipped spec prose should say "a later release" and the ordering should live in one
place** — proposed during this brainstorm, not yet acted on.
